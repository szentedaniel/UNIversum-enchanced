# Ticket #332 (the spectator dashboard target and the cross-Room gauge test) — extension points and gotchas

Branch `agent/issue-332-factory-review-follow-ups-329`, from main. Review follow-ups to #329, the follow-up of #250. No production source, protocol, stored-state or logger redact change.

## What landed

- **The `spectators` gauge is on the dashboard.** `monitoring/grafana/dashboards/universum.json`'s "Connections" timeseries (panel id 9, `gridPos` x 8, y 5, w 8, h 8) keeps targets A `players_connected` ("connected") and B `seats_held_disconnected` ("held, disconnected"); #332 added target C, `refId` "C", `datasource` `prometheus`/`prometheus`, `expr` "spectators" and `legendFormat` "watching". No panel was added and no `gridPos` moved. `spectator_joins_total` stays off the dashboard: no existing panel fits a join rate.
- **`expectSeatsUnchanged(scrape)`** in `apps/server/test/observability.test.ts`, next to `sample()`: one scrape's Seat metrics are untouched — `players_connected` 2, `seats_held_disconnected` and `seat_drops_total` 0. The existing spectator test calls it after the join, the drop and the leave. `spectator_joins_total` is not a Seat metric and its expected value differs per step, so each call site asserts it beside the helper: 1 after the join, 1 after the drop, 2 after the leave.
- **`pollSpectators(scrape, n)`** in the same file polls the labelless `spectators` gauge until it reads `n`; both spectator tests use it instead of repeating the `expect.poll` body. **`startedRoom(server)`** creates a `maxPlayers: 2` Room, seats a Guest, sends `Start`, reads both `game` pushes and returns `{ creator, view }` — the creator, and the first `game` push's `view` the single-Room test needs for a spectator's `Roll` `turn` — so both tests build their Rooms in one line each.
- **"sums the spectators across Rooms, and one leaving drops the sum by one"** in the same `describe("metrics")`: two `startedRoom()`s, two spectators watching the first and one watching the second; `expect.poll` on `sample(scrape, "spectators")` for 3, then the second Room's spectator `leave()`s and the poll expects 2; the join counter ends at 3 and `players_connected` is `expect.poll`ed to 4 once the spectator poll has settled.

## Gotchas

- **The gauge is labelless, so the test carries the expected sum.** There is no per-Room series to read; the test knows how many spectators it joined and polls for that number, exactly as the existing single-Room test does. Do not add a Room-code label to the query or the scrape to make a test easier to write.
- **The join counter is not a Seat metric.** It is asserted inline at each call site rather than inside `expectSeatsUnchanged`; the leave step asserts it only after its gauge poll has settled, so no in-flight leave can move it. The values stay 1 after the join, 1 after the drop and 2 after the leave.
- **Both Rooms are started before their spectators join.** Two connected Guests fill each `maxPlayers: 2` Room, and the two-Room test polls `players_connected` to 4 there — which is why `expectSeatsUnchanged`'s fixed 2 fits only the single-Room test. Watching a Lobby is allowed: `authorize`'s `watch` branch checks only `spectatorsFull()` and the password, never `room.game`, and the logs test watches a one-Seat Lobby. A started Room stays out of the Lobby-disposal path: `disposeIfAbandoned` returns as soon as `this.game` is set, and `startGame` has switched `autoDispose` off.
- **Colyseus joins and leaves land asynchronously.** Every `spectators` read is `pollSpectators`'s `expect.poll`, never a single scrape, and so is the two-Room test's `players_connected` 4; the joins counter is asserted after the leave poll has settled so no in-flight leave can move it.

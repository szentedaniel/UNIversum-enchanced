# Ticket #248 (a Room admits spectators, read-only and capped) — extension points and gotchas

Branch `agent/issue-248-server-a-room-admits-spectators-read-only-and-capp`, from main at `327ef15`. The server half of spec #179; #249–#253 build on it. The rules engine, `GameState` and the stored snapshot are untouched.

## What landed

- **`GameRoom.authorize`** admits `join.data.watch === true` as a spectator: the Room must exist, its spectator set must be under the cap, and its password (when it has one) must match. It skips the Guest-token `seatOfToken` path entirely, so a watch join carrying a Guest's token never takes that Seat back; a spectator may watch a full Lobby, a running game and an ended Room. The password work moved into a local `checkPassword` closure shared by the Player and spectator branches.
- **`GameRoom.onJoin`** releases `auth.reservation` first, as for a Seat, then for a spectator re-checks the cap, checks the password only when `auth.code` is not this Room, adds the session id to `#spectators` and calls `sendSpectatorCurrent`. A spectator gets **no `welcome`** (it has no Player id) and takes no Seat.
- **`#spectators: Set<string>`** (session ids) is the only spectator state: Room memory, never in `seats`, `GameState`, `RoomStore` or the Room metadata. `onLeave` deletes the session id next to the flood meters. A dropped spectator is not `allowReconnection`ed (`onDrop` finds no Seat and returns), so Colyseus calls `onLeave` straight away: no Seat hold, no Bot, no reconnection token.
- **Read-only by the Room.** `onIntent` finds no Seat for a spectator and answers `SPECTATOR_READ_ONLY`, before `metrics.intentHandled` (so it is not a Player intent sample). `onChat` still ignores a non-seated sender; spectator chat is out of scope.
- **The cap.** `DEFAULT_LIMITS.spectatorsPerRoom` (10, `LIMIT_SPECTATORS_PER_ROOM`) is the owner's number to pick in review. `onCreate` adds it to `maxClients` (`maxPlayers * 2 + spectatorsPerRoom`), because Colyseus counts spectators in `clients` and sets the listing's `locked` at `maxClients`, which makes `joinById` answer 522 before `onAuth`: without the spectator share, a Guest-token rejoin (another tab) would be refused. `authorize` and `onJoin` cap the spectator set itself with `SPECTATORS_FULL` (HTTP 409 in `STATUS`).
- **Disposal.** `disposeIfAbandoned` now looks at non-spectator clients, so a Lobby whose last Guest left is disposed even while spectators watch (Colyseus's own autoDispose would otherwise keep it alive while any client is connected). A Seat held for a dropped Guest still keeps the Lobby (Colyseus's reserved client), as does any non-spectator client mid-join. A running game still skips disposal and follows the usual Bot-only retention; `gauges()` and `isSeatConnected` stay Seat-only.
- **Protocol and web text.** `REJECTION_CODES` gained `SPECTATORS_FULL` and `SPECTATOR_READ_ONLY`; `apps/web/src/text.ts`'s `REJECTIONS` and `messages/{hu,en,de}.json` have `rejection_spectators_full` and `rejection_spectator_read_only`.
- **Tests.** `apps/server/test/spectators.test.ts` starts its server with `spectatorsPerRoom: 2` (so the cap is cheap to fill) and covers: a Lobby/full Lobby/started game join, the same `GameMessage` as a Player, no `welcome`, the password gate, a watch join carrying a Guest token, the snapshot unchanged, both read-only rejections, the cap, a Guest-token rejoin with spectators at the cap (the `maxClients` hazard), a dropped spectator's freed slot, a Lobby kept by a dropped Guest's Seat while a spectator watches, a Lobby disposed with spectators only, and a running game with spectators only waiting for its usual retention. The last test moves the shared `ManualScheduler` a minute, so keep it last.

## Extension points and gotchas for #249–#253

- **The spectator count.** `#spectators.size` is the count; it is private, so a count helper lives in `GameRoom` (as #249 plans). A join/leave push must be added where `sendSpectatorCurrent` and `onLeave`'s delete run, or from the same helpers.
- **Message shapes.** `LobbyMessage`/`GameMessage` have no `spectators` field yet (#249). `sendSpectatorCurrent` builds a fresh `lobbyMessage()`/`gamePush()`, so a count added to those two builders reaches a joining spectator; `broadcastLobby` and the driver's `publish` need it too.
- **The web side.** No web code reads `watch` or the two Rejection codes yet; #251 adds `watchRoom`, the spectator role, the read-only Game screen and the `SPECTATORS_FULL` text. A spectator's client gets no `welcome`, so the join path must not wait for one.
- **Metrics.** `gauges()` still reports Seats only; #250 adds the spectator gauge and the join/leave counter. A spectator's join/leave must not move `seats_connected`, `seats_held_disconnected` or the Seat disconnect counter (it does not today).
- **Do not relist a started Room** because spectators arrived: `unlist()` is only for the Lobby list, and `syncListing` runs from `broadcastLobby`, which a spectator join deliberately does not call.
- **Any new iteration over `this.clients`** for game facts stays Seat-only. The one deliberate client-set read is `disposeIfAbandoned`'s "a non-spectator client is a Guest" check.
